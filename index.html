01

Foundations: what an agent actually is

A chatbot answers. An agent decides what to do next, does it, looks at the result and repeats until the goal is met. Everything else in this guide is plumbing around that loop.

The four parts

1 · Brain (LLM)

Reasons about the goal, picks the next action, writes tool arguments. Choose by task: a small fast model for routing and extraction, a larger one for planning and hard reasoning.

2 · Memory

Buffer: the current conversation. Working: scratchpad for the current task (plan, intermediate results). Long-term: facts and past experience in a vector store or database, retrieved when relevant.

3 · Tools

Retrieval (search, RAG, SQL), action (create ticket, send email), analysis (code interpreter), communication (call another agent). Tools are how an agent touches the world.

4 · Planner

Breaks a goal into steps, orders them, and revises when a step fails. Sometimes explicit (a plan object), often implicit in the model's reasoning.

The loop

Every agent runs some version of Think → Act → Observe, with a stop check each turn. Stop when the goal is met, when a step limit is hit, or when a human must decide.

A complete agent in about 40 lines, no framework

Frameworks hide this loop. Write it once so you know what they are doing for you. The llm() function is a stand-in for any model API that supports tool calling.

agent_loop.py
import json

# 1. Tools: plain functions plus a schema the model can read.
def get_order_status(order_id: str) -> dict:
    return {"order_id": order_id, "status": "shipped", "eta": "2026-10-22"}

TOOLS = {"get_order_status": get_order_status}
TOOL_SCHEMAS = [{
    "name": "get_order_status",
    "description": "Look up the shipping status of ONE order by its ID. "
                   "Use when the customer asks where an order is.",
    "parameters": {"type": "object",
                   "properties": {"order_id": {"type": "string"}},
                   "required": ["order_id"]},
}]

def llm(messages, tools):
    """Call your model here. Return either
       {"type": "text", "text": "..."}   or
       {"type": "tool_call", "name": "...", "args": {...}, "id": "..."}"""
    raise NotImplementedError

def run_agent(goal: str, max_steps: int = 8) -> str:
    messages = [
        {"role": "system", "content": "You are a support agent. Use tools; never guess."},
        {"role": "user", "content": goal},
    ]
    for _ in range(max_steps):                       # hard step limit
        reply = llm(messages, TOOL_SCHEMAS)           # THINK
        if reply["type"] == "text":                   # stop check
            return reply["text"]
        try:                                          # ACT
            result = TOOLS[reply["name"]](**reply["args"])
        except Exception as e:                        # errors are observations too
            result = {"error": str(e)}
        messages.append({"role": "assistant", "tool_call": reply})
        messages.append({"role": "tool", "id": reply["id"],   # OBSERVE
                         "content": json.dumps(result)})
    return "Stopped: step limit reached. Escalating to a human."

Four patterns that cover most designs

PatternWhat it doesUse whenWatch out for
Tool useModel calls functions and reads results.Almost always. It is the base.Vague tool descriptions cause wrong calls.
ReflectionAgent critiques its own output, then revises.Writing, code, anything with a checkable standard.Extra latency and cost; cap at 1-2 rounds.
PlanningMake a plan first, then execute step by step.Multi-step tasks with dependencies.Plans go stale; allow re-planning on failure.
Multi-agentSpecialist agents coordinated by a manager, peers or a marketplace.Distinct skills, separate teams or vendors.Coordination cost. Start with one agent and split only when needed.

Rules of thumb that save weeks

  • Keep 3 to 5 tools per agent. Accuracy drops as the tool list grows. Past that, split into specialist agents.
  • Write tool descriptions like onboarding notes. Say what it does, when to use it, and when not to. Name parameters clearly and give units and formats.
  • Return small, structured tool results. Large raw payloads burn context and confuse the model.
  • Run independent tool calls in parallel, stream partial output, cache repeated lookups, and retry transient failures with backoff.
  • Always set a step limit and a timeout. Agents can loop forever, and the bill keeps running.
  • Latency budgets: about 2 seconds for simple lookups, 10 seconds for a multi-tool answer, 30 seconds before you need a progress indicator or an async job.
02

The two protocols: MCP for tools, A2A for agents

Think of MCP as the USB port between an agent and its tools, and A2A as the phone line between one agent and another. They solve different problems and you will usually use both.

MCP (Model Context Protocol)A2A (Agent2Agent)
ConnectsAn agent to tools and dataAn agent to another agent
OriginAnthropic, November 2024; now under the Linux Foundation's Agentic AI FoundationGoogle, April 2025; now a Linux Foundation project, v1.0 released in 2026
ExposesTools, resources, promptsSkills advertised in an Agent Card; tasks with a lifecycle
DiscoveryYou configure the server URL or commandFetch the Agent Card at /.well-known/agent-card.json
Transportstdio (local) or Streamable HTTP (remote)JSON-RPC over HTTP, gRPC, or HTTP+JSON; streaming and push notifications
Best forDeterministic calls: query a database, call an APIDelegating a goal to an autonomous peer that may take time and ask questions
StateMostly stateless request and responseStateful tasks: submitted, working, input-required, completed, failed and more
Rule of thumb

If the callee is a function with a fixed contract, expose it as an MCP tool. If the callee reasons, may take minutes, or belongs to another team, expose it as an A2A agent.

MCP in one page

An MCP server advertises tools (callable functions with JSON Schema inputs), resources (readable data) and prompts (reusable templates). A client lists them and calls them. Use stdio for a local subprocess and Streamable HTTP for anything remote. The older "HTTP+SSE" transport is deprecated, so if a tutorial tells you to use it, translate to Streamable HTTP.

Here is a complete, working MCP server using the official Python SDK's FastMCP helper. Run it locally with stdio first, then switch the last line to serve over HTTP.

orders_mcp.py (pip install "mcp[cli]")
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("orders")

@mcp.tool()
def get_order_status(order_id: str) -> dict:
    """Look up the shipping status of one order by ID.
    Use when a customer asks where their order is.
    Args:
        order_id: The order ID, for example "A-1042".
    """
    # Replace with a real database or API call.
    return {"order_id": order_id, "status": "shipped", "eta": "2026-10-22"}

if __name__ == "__main__":
    # Local development over stdio:
    # mcp.run()
    # Remote over Streamable HTTP (serves at /mcp on port 8000):
    mcp.run(transport="streamable-http")

A2A in one page

An A2A server publishes an Agent Card: who it is, what skills it has, where to call it and how to authenticate. A client fetches the card, then sends a message. The server answers with a direct message or creates a task that moves through states and produces artifacts as output.

A2A has two live wire formats

Spec v1.0 renamed things from v0.3: the card moved from agent.json to agent-card.json, a single url became a supportedInterfaces list, methods became SendMessage, GetTask and so on, task states gained a TASK_STATE_ prefix, and clients send an A2A-Version: 1.0 header (no header means 0.3). Many deployed agents and cloud docs still speak 0.3. Before wiring two agents together, fetch each card and check which version it declares.

Agent Card, v1.0 style verify fields against the spec

/.well-known/agent-card.json
{
  "name": "Order Support Agent",
  "description": "Answers order status and returns questions.",
  "version": "1.0.0",
  "supportedInterfaces": [
    { "url": "https://orders.example.com/a2a", "protocolBinding": "JSONRPC", "protocolVersion": "1.0" }
  ],
  "capabilities": { "streaming": true, "pushNotifications": false },
  "defaultInputModes": ["text/plain"],
  "defaultOutputModes": ["text/plain"],
  "skills": [
    {
      "id": "order-status",
      "name": "Order status",
      "description": "Look up shipping status for an order ID.",
      "tags": ["orders", "support"],
      "examples": ["Where is order A-1042?"]
    }
  ]
}

Calling it over JSON-RPC

The 0.3 style below is the one most deployed agents (including current AWS AgentCore examples) accept. It is plain HTTP, so you can test any A2A agent from a terminal.

A2A 0.3 style: message/send
curl -s https://orders.example.com/a2a \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "jsonrpc": "2.0",
    "id": "1",
    "method": "message/send",
    "params": {
      "message": {
        "role": "user",
        "messageId": "msg-001",
        "parts": [{ "kind": "text", "text": "Where is order A-1042?" }]
      }
    }
  }'
A2A 1.0 style: SendMessage (verify against the v1.0 spec)
curl -s https://orders.example.com/a2a \
  -H "Content-Type: application/json" \
  -H "A2A-Version: 1.0" \
  -H "Authorization: Bearer $TOKEN" \
  -d '{
    "jsonrpc": "2.0",
    "id": "1",
    "method": "SendMessage",
    "params": {
      "message": {
        "role": "ROLE_USER",
        "messageId": "msg-001",
        "parts": [{ "text": "Where is order A-1042?" }]
      }
    }
  }'

Task lifecycle

A long-running request returns a task you can poll with GetTask, stream, or receive via push notification. States: submitted, working, input-required (the agent needs more from you), auth-required, completed, failed, canceled, rejected and unknown. Treat input-required as a first-class path: it is how an agent asks a human or its caller for missing information.

03

Reference architecture and flow patterns

This shape works on every cloud. Swap the platform band for GCP, AWS or OCI services and the structure stays the same.

Choosing a flow

Single agent + MCP tools

Start here. One agent, 3 to 5 tools, one team. Most business automations never need more.

Orchestrator + specialists

A manager agent delegates to specialists in-process (sub-agents) or over A2A. Choose A2A when specialists belong to other teams, clouds or vendors.

Sequential pipeline

Fixed stages: extract, validate, enrich, write. Use workflow agents or a plain state machine. Do not pay for LLM planning when the order is known.

Peer collaboration or marketplace

Agents discover each other through a registry and negotiate. Powerful, hardest to govern. Add only with identity, quotas and audit logging in place.

Recommended path

Single agent with MCP tools → add a reflection pass → split one specialist behind A2A → add a second cloud only when data or policy forces you to. Each step should be justified by a measured problem.

Build tracks: the same eight steps on each cloud

Pick a cloud. Every track follows the same order: set up, build the agent, add MCP tools, expose it over A2A, deploy, secure identity, observe, and avoid the known traps. The sample agent is the order-support agent from earlier, so you can compare the code across platforms.

Build the agent with a tool

ADK turns a typed Python function with a docstring into a tool. The docstring is what the model reads, so write it carefully.

order_agent/agent.py
from google.adk.agents import Agent

def get_order_status(order_id: str) -> dict:
    """Look up the shipping status of one order by ID.

    Use when a customer asks where their order is.

    Args:
        order_id: The order ID, for example "A-1042".

    Returns:
        A dict with status and eta, or an error message.
    """
    return {"order_id": order_id, "status": "shipped", "eta": "2026-10-22"}

root_agent = Agent(
    name="order_support_agent",
    model="gemini-2.5-flash",   # replace with a current Gemini model you can use
    description="Answers order status questions.",   # other agents read this
    instruction=(
        "You help customers with orders. Always call a tool for order data. "
        "If an order ID is missing, ask for it. Never invent order details."
    ),
    tools=[get_order_status],
)

adk web      # local dev UI with traces; run from the folder that contains order_agent/
adk run order_agent

Add MCP tools

ADK connects to an MCP server through MCPToolset. For a remote server use Streamable HTTP connection parameters. Google also offers managed remote MCP servers for its own services, controlled by IAM and Model Armor; check the current list in Google's docs and use those instead of building your own where they fit.

order_agent/agent.py (replace the tools list)
from google.adk.agents import Agent
from google.adk.tools.mcp_tool.mcp_toolset import MCPToolset
from google.adk.tools.mcp_tool.mcp_session_manager import StreamableHTTPConnectionParams

orders_tools = MCPToolset(
    connection_params=StreamableHTTPConnectionParams(
        url="https://orders-mcp-xxxx.a.run.app/mcp",
        headers={"Authorization": "Bearer <ID_TOKEN>"},   # see step 6 for real auth
    ),
    tool_filter=["get_order_status"],   # expose only what this agent needs
)

root_agent = Agent(
    name="order_support_agent",
    model="gemini-2.5-flash",
    instruction="You help customers with orders. Always use tools for order data.",
    tools=[orders_tools],
)

Identity, secrets and guardrails

  • Service-to-service calls: give each service its own service account and grant the caller roles/run.invoker on the callee. The caller sends a Google-signed ID token with the callee's URL as audience.
  • Secrets: store API keys in Secret Manager, grant roles/secretmanager.secretAccessor to the runtime service account, and inject as environment variables or read at startup. Never ship a .env file in the image.
  • Guardrails: put Model Armor in front of prompts and responses to screen for injection and data leakage, and use ADK callbacks to validate tool arguments before they run.
  • Agent identity: Agent Runtime supports per-agent identities so IAM policies can name the agent, not a shared account. Check current docs for the setup commands.

Gotchas on Google Cloud

  • Naming has shifted (Vertex AI Agent Engine, Agent Runtime, Gemini Enterprise Agent Platform). Search docs by both names.
  • The environment variable that switches to enterprise-hosted Gemini was renamed in recent docs; a wrong name silently falls back to API-key mode.
  • The agent folder must contain root_agent and an __init__.py importing the module, or deploy and adk web find nothing.
  • Cloud Run default compute service account needs Cloud Build builder permission for adk deploy cloud_run to succeed.
  • Agent Card version mismatch (0.3 vs 1.0) is the usual cause of "A2A call returns 404 or method not found".

AWS's path pairs Strands Agents (an open-source Python and TypeScript SDK) with Amazon Bedrock AgentCore, a set of managed services: Runtime (hosting), Gateway (turn APIs and Lambdas into MCP tools), Memory, Identity, Observability, Policy, plus Code Interpreter and Browser. You are not locked in: AgentCore Runtime hosts any framework that can speak its protocol.

Build the agent with a tool

    model=model,
    system_prompt="You help customers with orders. Always use tools for order data.",

Add MCP tools, directly or through Gateway

Direct MCP server. Strands' MCPClient wraps an MCP connection. Keep tool use inside the context manager so the session stays open.

python
from strands import Agent
from strands.tools.mcp.mcp_client import MCPClient
from mcp.client.streamable_http import streamablehttp_client

mcp_client = MCPClient(lambda: streamablehttp_client("https://orders-mcp.example.com/mcp"))

with mcp_client:
    tools = mcp_client.list_tools_sync()
    agent = Agent(model=model, tools=tools)
    print(agent("Where is order A-1042?"))

Expose and call agents over A2A

AgentCore Runtime supports an A2A protocol mode. The runtime serves A2A on port 9000 at /, MCP on port 8000 at /mcp, and plain HTTP on 8080 at /invocations. Choose A2A when you create the project; the scaffolded entrypoint wraps your Strands agent with an A2A executor.

If you are not using the scaffold, Strands ships its own A2A server that works in any container:

a2a_server.py (pip install "strands-agents[a2a]")
from strands import Agent
from strands.multiagent.a2a import A2AServer

agent = Agent(
    name="Order Support Agent",
    description="Answers order status questions.",
    tools=[get_order_status],
)

server = A2AServer(agent=agent, host="0.0.0.0", port=9000)
server.serve()      # Agent Card is served at /.well-known/agent-card.json

Calling a deployed AgentCore agent uses its runtime ARN. The exact URL, headers and session header are documented per protocol:

shape of a remote call (verify header names in the AgentCore A2A docs)
# 1) Fetch the card
curl -s "https://bedrock-agentcore.REGION.amazonaws.com/runtimes/ENCODED_ARN/invocations/.well-known/agent-card.json" \
  -H "Authorization: Bearer $TOKEN"

# 2) Send a message (A2A JSON-RPC, 0.3 style as in current AWS examples)
curl -s "https://bedrock-agentcore.REGION.amazonaws.com/runtimes/ENCODED_ARN/invocations/" \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":"1","method":"message/send","params":{"message":{"role":"user","messageId":"m1","parts":[{"kind":"text","text":"Where is order A-1042?"}]}}}'
# ENCODED_ARN is the runtime ARN, URL-encoded.

To call any A2A agent from Python on any cloud, use the open-source a2a-sdk client, or the plain HTTP calls shown in section 02. Both work against AgentCore, Cloud Run and OCI alike.

Identity, secrets and guardrails

  • Inbound auth: AgentCore Runtime accepts AWS SigV4 (IAM) or OAuth/JWT. Use IAM for AWS-to-AWS calls and JWT for anything crossing accounts, clouds or customers.
  • Outbound auth: AgentCore Identity stores OAuth credentials for third-party APIs and supports on-behalf-of-user flows, so the agent acts with the user's permissions, not a super-user key.
  • Secrets: AWS Secrets Manager, read via the runtime's execution role. Never bake keys into the image or the agent's system prompt.
  • Guardrails: Amazon Bedrock Guardrails filter content, deny topics, redact PII and check grounding; apply them to the model and to tool responses. AgentCore Policy lets you restrict which tools an agent may call.
  • Least privilege: the execution role should list the exact Lambda ARNs, secrets and models the agent needs, nothing more.

Observe and evaluate

  • AgentCore Observability emits OpenTelemetry traces to CloudWatch's generative AI dashboards, with spans for model calls, tool calls and memory access.
  • Add the AWS Distro for OpenTelemetry (ADOT) package to your container if you host outside the scaffold.
  • Build an evaluation set and run it in CI against a dev deployment before promoting to prod.

Gotchas on AWS

  • Model access: "access denied" on first call usually means you have not enabled that model in Bedrock for your region and account.
  • Gateway needs 30 to 60 seconds after creation before DNS resolves. Retry before debugging.
  • Gateway tool lists are paginated; follow the pagination token or your agent sees only the first page of tools.
  • Different protocol, different port and path. A2A agents answering on 8080 or MCP servers answering on 9000 will fail health checks.
  • AWS docs for A2A still show the 0.3 wire format; if your orchestrator speaks 1.0, check for version negotiation or use a 0.3-compatible client.
  • Lambda is the wrong home for streaming or long tasks. Use AgentCore Runtime or Fargate.

Oracle's path has three layers. The OCI Generative AI Responses API is an OpenAI-compatible endpoint with built-in tools (file search, code interpreter, function calling, and remote MCP calling) and managed conversation memory. OCI Agent Development Kit (ADK) and open frameworks (LangGraph, AutoGen, LangChain) cover custom logic. For data work, the Autonomous AI Database MCP Server lets agents query your database through governed tools. If you run Oracle Fusion Applications, AI Agent Studio adds ready-made agents that speak MCP and A2A.

Call a model and keep state

Use the standard OpenAI SDK, pointed at your region's endpoint. The Responses API manages conversation state for you through previous_response_id.

hello_oci.py
from openai import OpenAI

REGION = "us-chicago-1"   # a region where Generative AI is available to you

client = OpenAI(
    base_url=f"https://inference.generativeai.{REGION}.oci.oraclecloud.com/openai/v1",
    api_key="<your-generative-ai-api-key>",
    project="<your-project-ocid>",
)

r1 = client.responses.create(
    model="xai.grok-4-1-fast-reasoning",   # or google.gemini-2.5-flash, openai.gpt-oss-120b, ...
    input="My order is A-1042. Remember that.",
)
print(r1.output_text)

r2 = client.responses.create(
    model="xai.grok-4-1-fast-reasoning",
    input="What was my order ID?",
    previous_response_id=r1.id,             # service-managed state
)
print(r2.output_text)

IAM authentication (recommended for production) sets api_key="not-used" and passes an HTTP client that signs requests with OCI credentials. The helper offers user-principal, session-token and resource-principal variants; use resource principal when the code runs inside OCI.

    api_key="not-used",
    project="<your-project-ocid>",
    http_client=httpx.Client(auth=OciResourcePrincipalAuth()),

Project memory

Projects can enable short-term memory compaction (summarises recent history to save tokens) and long-term memory (extracts facts into embeddings). Both are chosen at project creation with specific models and cannot be turned off later without deleting the project, so decide deliberately. Retention for responses and conversations is configurable up to 720 hours.

Add tools: functions and remote MCP

Two ways to give the agent tools. Function calling: you run the tool and return the result (full control, same pattern as the loop in section 01). MCP calling: OCI calls your remote MCP server for you during the request, saving a round trip.

python
resp = client.responses.create(
    model="openai.gpt-oss-120b",
    tools=[{
        "type": "mcp",
        "server_label": "orders",
        "server_description": "Order lookups for support.",
        "server_url": "https://orders-mcp.example.com/mcp",   # must be reachable by OCI over HTTPS
        "allowed_tools": ["get_order_status"],               # least privilege
        "require_approval": "never",                          # use only for read-only tools
        "authorization": "<raw-access-token>",                # token only, no "Bearer " prefix
    }],
    input="Where is order A-1042?",
)
print(resp.output_text)
  • The server must be reachable from OCI's service network over public HTTPS, so protect it with a token and an allow-list, not by hiding the URL.
  • Tool support in the Responses API is available through the API only, and the model decides whether to use a tool.
  • Other built-in tools: file_search (vector stores), code_interpreter (managed Python sandbox).

Give agents your data with the Autonomous Database MCP Server

Autonomous AI Database can expose an MCP endpoint, so agents query data where it lives under the database's own security. Enable it with a free-form tag on the instance, then register Select AI Agent tools.

  1. In the console, add a free-form tag to the Autonomous AI Database Serverless instance. Name: adb$feature. Value: {"name":"mcp_server","enable":true}.
  2. The endpoint is https://dataaccess.adb.REGION.oraclecloudapps.com/adb/mcp/v1/databases/DATABASE_OCID. Private-endpoint databases get a prefixed hostname and are reachable only inside your VCN.
  3. Create a tool with DBMS_CLOUD_AI_AGENT.CREATE_TOOL, backed by a PL/SQL function. Oracle's walkthrough uses a paginated RUN_SQL function with QUERY, OFFSET and LIMIT inputs, where the query must be a SELECT with no trailing semicolon.
  4. Connect with a bearer token. Point the Responses API MCP tool above, or the OCI ADK below, at the endpoint.
Do not hand an agent free-form SQL on a production schema

Run it as a read-only database user, expose views instead of base tables, cap row counts, and prefer narrow tools ("monthly revenue by region") over a generic SQL runner.

Identity, secrets and guardrails

  • Workload identity: use resource principals (dynamic groups plus policies) so your container needs no stored credentials.
  • Secrets: OCI Vault. Read secrets at startup through the resource principal.
  • Network: keep agents and MCP servers in private subnets; expose only through API Gateway or a load balancer with WAF.
  • Content safety: use the Generative AI service guardrails for content moderation, prompt-injection and PII checks, and add your own validation before write actions.
  • Data access: for database agents rely on database roles and Virtual Private Database policies so the agent cannot see what the user could not.

Observe and evaluate

  • Send application logs to OCI Logging and traces to OCI Application Performance Monitoring using OpenTelemetry exporters.
  • Set alarms on error rate, latency and token consumption in OCI Monitoring.
  • Keep a fixed evaluation set and run it after every prompt, model or tool change.

Gotchas on Oracle Cloud

  • Model availability varies by region and by on-demand versus dedicated mode. In dedicated mode the model value is your cluster endpoint OCID and the request must go to that cluster's region.
  • The Responses API authorization field takes the raw token. Including "Bearer " is a common cause of 401s.
  • Memory settings on a project are one-way decisions.
  • The older /20231130/actions/v1 inference path appears in earlier tutorials; current docs use /openai/v1. Use the one your docs page shows.
  • OCIR login uses the tenancy namespace and an auth token, not your console password.
05

Cross-cloud agent flows

Real companies have data on one cloud, apps on another and a SaaS vendor on a third. A2A is designed for exactly this: each agent stays where its data and team live, and the card is the contract.

Making it work

1 · Agree on the A2A version

Fetch each Agent Card and read its protocol version. Pin all agents to one version, or put a thin adapter in front of the old ones.

2 · One identity story

Use an OIDC provider all three clouds trust (Okta, Entra ID, Cognito, OCI IAM identity domain, Google identity). The caller gets a short-lived token via client-credentials and each agent validates issuer, audience and scope.

3 · Prefer federation to keys

Where a workload on one cloud needs to call a cloud API on another, use workload identity federation (GCP, AWS and OCI all support trusting an external OIDC identity) instead of copying long-lived keys.

4 · Treat the network as hostile

TLS everywhere, allow-lists on the callee, WAF or API gateway in front, rate limits per caller, and request size caps.

5 · Propagate trace context

Pass W3C traceparent on every A2A call so one user request shows as one trace across three clouds in your observability tool.

6 · Design for partial failure

Every remote call gets a timeout, a retry budget and a fallback answer. Return what you have and say what is missing.

orchestrator that talks to three clouds (ADK, shape)
from google.adk.agents import Agent
from google.adk.agents.remote_a2a_agent import RemoteA2aAgent

ops_aws = RemoteA2aAgent(
    name="ops_aws",
    description="Creates tickets and runs operational workflows (hosted on AWS).",
    agent_card="https://ops.example.com/.well-known/agent-card.json",
)
data_oci = RemoteA2aAgent(
    name="data_oci",
    description="Answers questions from the finance database (hosted on Oracle Cloud).",
    agent_card="https://data.example.com/.well-known/agent-card.json",
)

root_agent = Agent(
    name="concierge",
    model="gemini-2.5-flash",
    instruction=(
        "Route data questions to data_oci and operational requests to ops_aws. "
        "If a specialist is unavailable, say so and do not guess."
    ),
    sub_agents=[ops_aws, data_oci],
)
# Authentication: configure the RemoteA2aAgent's HTTP client to attach a bearer token.
# Parameter names for that vary by ADK release, so check the current ADK reference.
Where it breaks in practice

Most cross-cloud failures are not protocol bugs. They are expired tokens, mismatched audiences, card URLs that point at internal hostnames, and timeouts shorter than the remote agent's real latency. Test each hop with curl before you test the chain.

06

Security and governance

An agent is software that reads untrusted text and then takes actions. That combination needs more care than a normal API.

ThreatHow it happensDefences
Prompt injectionA web page, email, document or tool result contains instructions the model obeys.Treat all retrieved content as data, not commands. Require approval for risky actions. Separate "read" agents from "write" agents. Use cloud guardrails on inputs and outputs.
Tool misuseThe model calls a tool with harmful arguments, or calls one it should not.Validate arguments in code. Narrow tools. Allow-list tools per agent. Rate limit and cap amounts.
Privilege escalationOne agent holds broad credentials and is tricked into using them.Per-agent identity, least privilege, on-behalf-of-user tokens, short-lived credentials.
Memory poisoningFalse facts are written into long-term memory and reused later.Write to memory only from trusted flows, tag provenance, expire entries, allow review and deletion.
Malicious tool descriptionsAn untrusted MCP server ships tool descriptions that steer the model.Only connect servers you own or vet. Pin versions. Review tool descriptions on update.
Agent Card abuseA card claims skills it lacks, or points to an attacker's URL.Fetch cards only from allow-listed hosts over TLS. Verify signed cards where supported. Never auto-trust a newly discovered agent.
Data exfiltrationThe agent is induced to send sensitive data to an external tool or URL.Egress allow-lists, DLP or PII redaction, no open web tools next to sensitive data.
Runaway costLoops, huge contexts or a public endpoint burn budget.Step limits, token budgets, per-caller quotas, billing alerts, authenticated endpoints only.

Fix these patterns when you copy tutorials

  • Keyword filters as a safety layer. A list of banned words is not a defence. Use a real guardrail service plus argument validation and approvals.
  • Unauthenticated deploys. Remove --allow-unauthenticated and equivalents. Put identity in front of every agent and MCP server.
  • Secrets in .env files or code. Use Secret Manager, Secrets Manager or OCI Vault with a workload identity.
  • One god-mode service account. One identity per agent, each with its own narrow permissions.
  • No audit trail. Log every tool call with caller, arguments (redacted), result status and trace ID.

Human-in-the-loop, done properly

Classify tools by blast radius. Read-only tools can run freely. Reversible writes (add a comment) can run with logging. Irreversible or costly actions (refund, send email, delete, deploy) pause for approval, and the approval screen must show the exact arguments, not the model's summary of them. In A2A this maps to the input-required task state; in OCI ADK and ADK/Strands it is a callback or hook before the tool runs.

07

From demo to production

Most agent projects stall between "works on my laptop" and "I trust it with customers". Close that gap with evaluation, observability and a boring release process.

Evaluate before you ship, and after every change

  1. Build a golden set. 30 to 100 real requests with expected tool calls and acceptable answers. Include failure cases: missing information, tool errors, hostile input.
  2. Score three things. Did it choose the right tools in the right order (trajectory)? Is the final answer correct and grounded? Did it stay inside policy?
  3. Use model judges carefully. A judge model is useful for tone and completeness but must be calibrated against human labels on a sample.
  4. Run in CI. A prompt, model or tool-description change that lowers the score blocks the merge.
  5. Sample production traffic back into the golden set every week.

What to measure

Quality

Task success rate, tool-call accuracy, escalation rate, thumbs-down rate, groundedness.

Speed

P50 and P95 latency per step and end to end, time to first token, tool latency by tool.

Cost

Tokens per task, model calls per task, cost per successful task, cache hit rate.

Safety

Guardrail blocks, refused approvals, anomalous tool use, cross-agent call volume.

Release process

  • Version prompts, tool descriptions and Agent Cards in Git like code.
  • Promote through dev, staging and prod with the evaluation gate between each.
  • Ship behind a flag or to a small percentage of traffic first, and keep a one-command rollback.
  • Pin model versions. Re-run evaluations before moving to a newer model.

Launch checklist

Your ticks are saved in this browser only.

  • Every agent and MCP server requires authentication; none is public by accident.
  • Each agent has its own identity with least-privilege permissions.
  • No secrets in code, images or prompts; secrets come from a managed vault.
  • Step limit, timeout and token budget set on every agent loop.
  • Tools are narrow, validated in code, and each agent has 5 or fewer.
  • Irreversible actions require human approval showing exact arguments.
  • Guardrails on inputs and outputs, tested with injection examples.
  • Golden evaluation set exists and runs in CI.
  • Traces, logs and cost metrics visible, with alerts on errors and spend.
  • Trace context propagates across every agent hop.
  • A2A versions and Agent Cards verified between all agents.
  • Rollback tested; prompts, tools and cards are versioned.
  • Data retention, memory deletion and audit logging meet your policy.

Glossary

TermMeaning

SymptomLikely causeFix
Agent never calls the toolVague tool description or too many toolsRewrite the description with "use when"; cut to 3-5 tools.
